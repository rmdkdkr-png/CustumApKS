# 157 기획 — 조사·시안 비교 원문 (작업 기록)

기획서 본문은 `../기획서_리그_인게임메뉴.md`. 아래는 조사 세 갈래와 시안 세 개, 심사 셋의 원문 요약(영문 섞임).

## 조사 — 기술(게임 화면에 그리기)

Research A (in-game drawing tech for a league in-game menu): I measured all four moments on the Linux harness with the real bundled core (KO, plus JUE in one scenario). The post-match latch is the moment that matters most. There the core is not running, and no native code runs per frame. If the game is stepped even one frame, it rewrites the middle of plane 0 and the sprite table, and it leaves the latched picture for the next chapter about 6–8 frames later. So nothing can be drawn into VRAM in the middle of the screen at the latch.

The latched picture has the same layout in 6/6 runs (P1 win, P2 win, time over, JUE): black band at lines 0–31, stage with both fighters at lines 32–135 (no HUD and no text visible), black band at lines 136–151. Every pixel colour can be reproduced exactly from the palette values: 37/37 colours matched the 12-bit ×17 → RGB565 rule.

Recommendation: draw the league UI on a "virtual overlay plane" in native.c (덧판). Java renders the text into NGPC 2bpp tiles, a map and palettes, the same way RankVs does today. native.c composites them over g_fb at the game's own 160×152 grid with the game's colour rule, every vsync, including while the core is latched or paused. This needs no tile budget, no restore before saves, no clash checks, and it works the same over the title, a pause, the latch and the search card.

Drawing into VRAM (the practice.c / vsband.c way) still works in two places. On the title during search, the game rewrites nothing, there are 318 free tiles and 63 free sprites, and the title did not time out in 2 minutes. In the game's own PAUSE there are about 120–160 tiles in the ranges practice.c treats as safe and 12–18 free sprite slots, but a window must be drawn in both alternating bands. VRAM is not viable at the latch.

Input: the GL thread gets a fresh pad mask every vsync even while latched, but nothing native "ticks" then. A menu tick has to be added to nativeFrame outside the core step loop, or the menu logic has to live in Java's onDrawFrame.

### 제약

- Latch = core held: pace_steps returns 0, so there is no c_run and no league_tick_hub / practice_tick / look_tick at all. g_input is still refreshed every vsync by Java onDrawFrame (padMask|keyMask|axisMask), so the menu needs its own tick in nativeFrame outside the step loop, or its logic in Java on the GL thread.
- At the latch, VRAM edits cannot show in the middle of the screen. Running even one frame rewrites plane-0 rows 4-16 (260/260 cells) and the sprite table, and the game leaves the latched picture after 6 (app, runahead 2) / 8 (plain) frames for the next-chapter scene (MODE 241 SCR 0/2, 0x57C8 15→1B). Only plane-0 rows 0-3 (lines 0-31) and 17-18 (lines 136-151) persist.
- Latched picture layout is the same in 6/6 scenarios (KO/JUE, P1 win, P2 win, time over): black 0-31 · stage with both fighters 32-135 (no HUD, no text; the winner-plate cells rows 5-8 × columns 5-14 are still in VRAM but not displayed) · black 136-151. Decision → latch took 518-640 frames.
- Exact game colours can be reproduced: frame colour = palette 12-bit 0x0BGR, each nibble ×17 → RGB565 (verified 37/37 at the latch); native.c then expands to RGBA8888.
- g_fb sizes vary: 160×152; 640×608 when ngp_framegen_idle is on (sub 4); 288-wide core pillar frames (game area at x 64·sub); taller frames with the move-name or commentary band (may be at the top). A compositor must locate the 160×152 game rectangle.
- nativeFrameBuffer (screenshot «no overlay», launcher thumbnails) returns the raw g_fb, so composite into a separate buffer. Ghost filter and shaders run on whatever is uploaded.
- Mid-fight plane-0 windows (game PAUSE) must be drawn in both alternating bands, rows 4-16 and 19-31. 0x41F5 toggles 00/78 every 2 frames; a single band shows 2 frames on, 2 off. Force 0x41F7/0x41F8 to 0 while open (as practice.c does).
- VRAM tile budgets: title/search 318 free tiles and 63 free sprites; game PAUSE about 120-130 tiles in the safe ranges (0x0D8-0x105, then unused 0x060-0x1FF) and 12-18 free sprite slots; stage intro 80 (0x0D0-0x105, 0x0B6-0x0CF, already used by the VS band); latch not applicable. A leaderboard page needs 119-262 unique tiles depending on font.
- VRAM drawing needs byte-exact restore before saves (practice_before_save / league_hub_before_save pattern), tracking of game writes and sprite clashes, and must avoid 0x000-0x05F (HUD font) during fights.
- The game does not rewrite VRAM on the title under H_SEARCH, and did not time out to a demo in 7200 frames. While paused it does not touch chr, scroll or sprite RAM.
- Snapshot-present (serialize → run 1 → unserialize) is byte-exact. State 31,743 B, 2.9 ms (plain) / 4.3-4.6 ms (app) per cycle on host x86, so too slow for 60-fps animation on phones, and only the black bands show.
- Runtime fonts in assets today: only Galmuri11 regular/bold (pixel.ttf, pixel_b.ttf), usable at 12 px only: 13 Hangul per 160-px line, about 10 lines (about 7 in the 104-px stage area). Denser text needs Galmuri7 (8 px, one syllable per tile, 19-20 per line) or Galmuri9 (10 px, 15 per line) added as OFL subsets.
- NGPC-authentic look rules if kept: 8×8 cells, one 4-colour palette per cell (colour 0 transparent → 3 inks), 20×19 cells on screen.
- sizeof H must stay 628 (.prac compatibility) and LEAGUE_NHUB stays 15: new menu state and status go in separate structs and calls.
- Input bits: A = bit 0, B = bit 8, OPTION = bit 3, directions 4-7. SP fold bits 1/9/10/11 must be blocked together with A and B. In a ranked H_MATCH, OPTION currently passes to the game (its own PAUSE); the app pause pill sets g_paused (core stopped).
- No ROM-derived images anywhere shared: work/l*/latch.state, latch.fb565 and latch.vram in my scratch are core-derived and stay scratch-only. Menus must use our own tiles and fonts; game HUD palette values may be reused as colour constants.
- 120 Hz panels: nativeFrame runs at panel rate, so animate on a 60-Hz clock to keep the NGPC cadence.

### 기회

- Build one 'virtual overlay plane' (덧판) in native.c and use it for every league UI moment: title lobby (순위표 / 전적 before searching), an opaque in-game-styled search card over the 4× muted auto-pick (replacing the Java rankQ overlay), the VS band (could move off VRAM and drop its clash logic), a league pause menu, and the post-match result + continue/stop menu.
- Post-match menu that grows out of the latch's own cinematic letterbox: top band 160×32 = result header (승리! / LP Δ / tier), bottom band 160×16 = button hints, centre window over a dimmed or 1-px-dithered frozen stage showing the final poses.
- Reuse the RankVs pipeline: generalise it to a TileCanvas (text / mini / box / per-cell palette / encode without the 80-tile cap). It is already JVM-testable with the AWT font adapter.
- Reuse the game's HUD palette values as overlay colours for a native look: orange AFF/07F (timer), red FFF/00E (1P/COM), blue FFD/E70, white/grey FFF/666, red plate FFF/65F/00C.
- Animation inventory for 간지: palette-cycling gold border and VS flash, raster-style shutter or brush wipes via per-line offsets, katana-cursor quad gliding 1 px per frame, LP count-up, star fill, rank-up stamp, 1-2 px shake of the frozen frame, smooth leaderboard scroll.
- Menu SFX: the audio ring is empty while latched, so native PSG-style blips (NGPC-like square waves) can be mixed in for cursor and confirm sounds.
- On the title (search), VRAM drawing is cheap and safe (318 free tiles, 63 sprites, game idle) if a native-VRAM lobby is preferred; game-PAUSE windows can reuse practice.c's proven window machinery (two bands, pool, restore).
- Add Galmuri7 and Galmuri9 subset TTFs (OFL, same family as pixel.ttf; files exist in scratch prac1/fontdl) for dense leaderboard and record pages: 19-20 or 15 Hangul per line respectively.
- Touch: map taps inside gameBox to menu rows, in addition to the D-pad, A/B and physical pads.
- Post-match actions map 1:1 onto existing calls (rankNext(false) / rankRematch / hubReturn(-1) / rankNext(true) / prefStage), so no new native flow is needed for the continue/stop decision itself.

## 1. How the app draws on the game screen today (code at w149/int 4513cf0)

**practice.c — practice menu window (F7, lines ≈659–958)**
- Opening: an OPTION tap with no other buttons sends OPTION to the game, which sets its own pause (0x61D4 = 1). After 4 paused ticks the window is drawn.
- Window: 13 rows × 14 cells on plane 0 (scroll plane 1), columns 3–16. It is drawn twice, in rows 4–16 and again in rows 19–31.
  - During a fight the game alternates which plane-0 band lines 32–135 show (0x41F5 = 0 / 0x78, by raster).
  - Measured now during a league-match PAUSE: 0x41F5 = 00 00 78 78 00 00 78 78. A window in one band only shows 2 frames on, 2 off. In both bands it is stable (3840/3840 px every frame).
  - While the window is open, the raster X-scroll RAM bytes 0x41F7 and 0x41F8 are forced to 0, and the original values are put back on close.
- Tiles: borrowed lazily into a pool of at most 80. Candidates are tiles no cell of either plane and no sprite points at: 0x0D8–0x105 first, then 0x060–0x1FF. 0x000–0x05F is excluded (HUD font, digits, PAUSE).
  - Each frame it checks whether the game wrote over a borrowed tile, and drops that tile from the pool (pool_dead).
- Palettes: two plane-0 palettes that no plane-0 cell uses, preferred in the order 13, 14, 15, 12, 6, 2. Colours:
  - Text: FFF / 999 / 411 (white on dark navy).
  - Border and selection: 5EF / 29C / 411 (gold).
- Glyphs: practice_glyphs.h, baked at build time from Galmuri7 at 8 px. One syllable = one tile (62 glyphs), plus border, corner and cursor tiles that use the flip bits.
- Restore: cells, tiles and palettes are put back byte-exact on close, and also in practice_before_save, so states never contain the window.
- Closing: injects OPTION (practice_in_or) with up to 3 retries.
- Input: practice_in_block = P_ALL while open. Edge detection, auto-repeat after 18 frames then every 5, and a dir_lock for a direction held when the menu opened.
- Measured during the PAUSE: the game does not touch chr, scroll or sprite RAM (0 bytes changed in one frame).

**vsband.c — VS band (156)**
- Area: plane 0, rows 0–3 × columns 0–19 (the black band at the top of the stage intro).
- Content: Java-rendered tiles and map (RankVs → Emu.nativeHubVs → league_hub_vs).
- Tiles: 0x0D0–0x105 (54), then 0x0B6–0x0CF (26); 80 at most.
- Palettes: HUD palettes 2, 3, 4, 5, 9, 13, 14, which stay constant through the intro.
- It only stamps when all 80 cells are the game's blank tile 0x001.
- Every frame it checks that our tiles are still ours and that no sprite points at them; if either fails it withdraws the band and puts tiles back (clash).
- It re-stamps after the game's 0x1E01 rewrite, and restores in league_hub_before_save.

**league.c — glyph swaps on the game's own screens**
- hdr_put: rewrites the pixel data of the select-screen header tiles 0x150–0x163 in place («상대», «선택» from hub_glyphs.h).
- vp_put → vpanel.c: draws into free tiles 0x130–0x141 and repoints 18 cells (plane 1 rows 3–11 × columns 17–18). Used for stage and colour names (HUB_VLAB, LOOK_VLAB).
- menu_relabel: rewrites tiles 0x1BB and 0x1BC plus the row-14 cells on the title («리그 대전»), with ◀▶ in 0x12E and 0x12F.
- All of these are restored before saves.
- hub_glyphs.h and practice_glyphs.h are generated by Python at build time from Galmuri (OFL).
- Only RankVs renders Korean at runtime.

**RankVs.java — runtime Korean text → NGPC tiles**
- Ink = Android Paint, pixel.ttf (Galmuri11) at 12 px, anti-alias off.
- Adds our own 4×7 digits and a 5×5 star.
- One palette per 8×8 cell; when a cell is claimed twice, the first claim wins.
- encode() dedupes identical tiles into 2bpp tiles (rows 16-bit little-endian, leftmost pixel in the high bits) plus a map of (pal<<9)|index.
- Refuses output that needs more than 80 tiles. JVM-testable through an AWT font adapter (RankVsMain).

**Precedent inside the core**
- ss2comm_overlay_* (coretest2/build/ss2comm.c ≈2289–2420; libretro.c 1788, 1907): while its overlay is active, retro_run skips emulation and draws a window over the last frame with Galmuri11-Condensed at 11 px.
- The app does not use it. It shows that "menu over the frozen last frame" is an established pattern.

## 2. Presentation and input pipeline

**Presentation**
- cb_video converts each core frame (RGB565, or a 4× 640×608 "idle in-between" frame) into g_fb (RGBA) and sets g_fb_dirty.
- gl_draw uploads g_fb only when it is dirty, then draws it through the upscaler, grid, scanline and colour shaders and the CPU ghosting filter.
- nativeFrameBuffer returns the raw g_fb. It is used for screenshots ("no overlay") and launcher thumbnails.
- Frame sizes vary:
  - 160×152 normally.
  - 640×608 with ngp_framegen_idle (sub = 4).
  - 288 wide with core side pillars (game area offset 64 px).
  - Taller when a band is on (SVC move-name band or SS2 commentary; may sit at the top).

**Latch**
- nativeFrame calls pace_steps(paused = g_paused || !g_loaded || league_post_hold()). When paused it returns 0, so no c_run and no league_tick_hub / look_tick / practice_tick.
- The 153 latch also breaks out of the step loop right after the real frame that set it, so the last presented image is a real frame.
- While held, gl_draw keeps drawing the same texture.
- The latch is released only by reset, hub return, a new arm, a new hub, the practice hub, or core load/unload.

**Input**
- Java onDrawFrame (GL thread) builds in = padMask | keyMask | axisMask every vsync, then calls nativeSetInput and nativeFrame. This happens even while latched or paused, so the touch pad and physical pads keep working.
- There is already a pattern for blocking the game: rankQBlock plus qHeld, which keeps a held key from leaking into the game when an overlay closes.
- The native input callback is: (user & ~(league | practice | look blocks)) | or-bits.
- Bits:

  | NGPC button | libretro bit |
  |---|---|
  | A | 0 (JOYPAD_B) |
  | B | 8 (JOYPAD_A) |
  | OPTION | 3 (START) |
  | Directions | 4–7 |
  | SP fold bits | 1, 9, 10, 11 — must be blocked together with A and B (153 lesson) |

- In a ranked match (H_MATCH, kind 0) OPTION currently passes to the game, which shows its own PAUSE. The app's pause pill (pad bar) is a Java overlay plus g_paused, which stops the core completely.

## 4. Options for drawing the in-game menu

**A. Virtual overlay plane in native.c (RECOMMENDED)**
- State: up to about 1024 2bpp tiles, a map (for example 20×19, or taller for scrolling lists), 16 four-colour palettes in 12-bit 0x0BGR (colour 0 transparent, one palette per 8×8 cell, to keep NGPC rules), and an x/y offset.
- Optional extras: a per-line x-offset table (raster-style wipes and waves), a few sprite-like quads (cursor, emblem), and a base-frame treatment (none / dim / 1-px dither / black).
- Composite at gl_draw time into a separate buffer g_ov with the same size as g_fb, mapping colours with the core's exact rule. Scale by sub = g_fb_w / 160 (1 or 4). Offset into the game rectangle (64·sub for 288-wide frames; 32·sub if a top band is on).
- Upload g_ov instead of g_fb while the overlay is active. nativeFrameBuffer keeps returning the raw frame.
- Works identically:
  - over a held core (latch), over g_paused (app pause), over the running title, and over a running game (composited onto every presented frame, including runahead and 120 Hz synthetic frames);
  - as an opaque full-screen "상대 찾는 중" card over the 4× muted auto-pick, which would replace the Java rankQ overlay.
- Never touches core state, so there are no before_save hooks, no clash checks and no tile budget, and save states and autosaves are always clean.
- Java side: generalise RankVs into a TileCanvas (text, mini digits, box, per-cell palette, encode without the 80-tile cap).
- New JNI along the lines of nativeOvSet(tiles, map, w, h, pals, x, y, flags), nativeOvAnim(…) and nativeOvClear(). Keep new status in its own call (LEAGUE_NHUB stays 15).

**B. VRAM borrowing per moment (practice.c / vsband.c style)**
- Viable on the title during search (large free canvas, game idle), in the game's PAUSE (practice already proves it; at most about 80–130 tiles, both bands, 0x41F7/0x41F8 forced to 0), and in the intro (the band only).
- **Not viable at the latch.**
- Needs restore before saves, clash and rewrite tracking, and tile budgets.
- A full leaderboard page does not fit. Counted unique 8×8 tiles for an 11-row page:

  | Font | Unique tiles |
  |---|---|
  | Galmuri11 @12 | 262 |
  | Galmuri9 @10 | 186 |
  | Galmuri7 @8, pitch 8 | 119 |
  | Galmuri7 @8, pitch 12 | 158 |

**C. Snapshot-present at the latch**
- Each present: serialize, write VRAM, run 1 frame, unserialize.
- Only the top 160×32 and bottom 160×16 black bands show anything. It runs game code on every present and costs about 3–5 ms per present on x86 (more on a phone).
- At best usable for a static result strip in the top band. Not recommended.

**D. Java views styled like the game (today's result card)** — fallback only.

**E. Core-side overlay like ss2comm** — needs a core patch and a rebuild of the bundled core, and is less flexible. Not recommended.

- palette cycling: verified, a palette write shows on the next frame;

## 7. Input routing for the menu

- **While held or paused:** add an overlay tick in nativeFrame outside `while (steps < nsteps)` using g_input. Do edge detection and repeat there, and time animation on a 60-Hz clock, because nativeFrame runs at the panel rate (120 Hz on some phones). Alternatively run the menu state machine in Java onDrawFrame, which already has `in`.
- **While the game runs (title or PAUSE):** block all game bits, including the SP fold bits, and release held keys on close (qHeld pattern).
- **Coexisting with Java:** the pad bar, ask and sheet already take keys first in dispatchKeyEvent. onBackPressed currently maps hubCard → hubReturn(-1). Taps on gameBox can be mapped to menu rows.
- **Post-match actions map onto existing calls:**

  | Menu item | Existing call |

  | 다음 상대 | rankNext(false) → hubReturn(-4) + autopick (c_reset; league_hub_return clears the latch) |
  | 재대결 | rankRematch → -4 |
  | 그만 | hubReturn(-1) → title «리그 대전» |
  | 캐릭터 바꾸기 | rankNext(true) |
  | Stage ◀▶ | League prefStage |

## 8. Integration hazards

- sizeof H must stay 628 (.prac compatibility): new state goes outside H, like AP / APC / MY.
- LEAGUE_NHUB stays 15: callers with fixed 15-int buffers crashed when it grew.
- Ghosting: if the overlay is composited before ghost_apply, menu transitions get LCD trails. That is a design choice.
- Upscalers apply only at sub == 1, and will round glyph corners just as they do the game's own text.
- Landscape: Java banners sit over gameBox and must be hidden while the menu shows, as was done for the VS band.
- No ROM art: menus use only our own tiles and fonts. The game's HUD colours (palette values) can be reused as constants.

이 인벤토리는 156 코드를 읽어서만 만들었습니다(앱은 실행하지 않음). 한 줄 요약: 인게임 메뉴에 필요한 데이터는 거의 다 있는데, 그걸 보여 주는 화면이 게임 밖에만 있습니다. 데이터는 랭크 상태 전체(LP·티어·★·MMR·배치·무쌍 MR·강등 위기·연승·최고 기록·잡힌 상대), 시즌 줄과 통산 승패, 랭크 경기 기록, 상대별 전적, 4만 명 가상 풀 순위표(위 n명·내 주변·내 순위)까지 있습니다. 148 대기창용 함수 셋(오늘 전적 rankedToday, 첫 승 보너스 bonusLeft, 팁 RankTips)은 153 이후 아무도 안 부르는 상태라 바로 쓸 수 있습니다. 순위표와 전적은 LeagueActivity에만 있어서 보려면 코어를 내리고 게임을 나가야 합니다. 게임 안에 있는 것은 안내 띠, 짧은 찾기 겹창, VS 띠, 결과 카드, 확인 카드뿐입니다. 결과 카드는 «다음 상대·재대결·그만»과 스테이지 ◀▶·«캐릭터 바꾸기»만 있고 순위표·전적·리그 나가기 버튼이 없습니다. «그만»은 리그를 끝내는 게 아니라 리셋해서 타이틀로 갑니다. 경기 중에는 패드 바와 뒤로 카드(계속하기·나중에 이어하기·기권)가 전부이고, 기권할 때 LP 미리보기가 없습니다. 게임 자체 OPTION 일시정지는 랭크 경기에서 막혀 있지 않습니다. 없는 데이터는 이번 대전 세션 집계, 경기별 순위 변화, 라운드별 기록, 기권 경기의 내 캐릭터, 가상 플레이어의 실제 승패 변화, 「처음부터 다시」 이후 경기 목록, 닉네임 편집입니다.

### 제약

- 허브가 살아 있는 동안(liveHub) 새 시즌과 「처음부터 다시」는 막힙니다(League.resetBlockedWhy, League.java:1411-1416). 인게임 메뉴의 시즌 정보는 보기만 가능합니다.

## 조사 — 참고 게임·스타일

Research C (references and style) is done. The proposed look is a "먹·금·낙관" (ink, gold, red seal) style for the league in-game menu. It is built from the app's own 먹·금 theme and the game's HUD colours, and laid out on the NGPC's 20×19-cell grid. Pages: 결판 (shown automatically after a match: result seal, animated LP gauge, rank event, tags, cursor starting on 다음 상대), 쉼 (opened with OPTION during a match), 순위표 (filters, top-3 plates, my row highlighted, rival chain icon) and 전적 (totals, streaks, last 10 as ○●, a 5×3 grid by opponent character, rival line). The open transition, «칼집 열기», takes about 20 frames and pressing A skips it. I drew four 160×152 mock screens, a transition storyboard and palette/motif strips, using only Galmuri7/11 and hand-made pixel art; game graphics are grey placeholder blocks. Tile counts measured from the mocks: if each cell gets its own tile, three of the four pages need more than the 80-tile pool the existing practice menu uses (130/174/191; only the pause window fits at 78). With one Hangul syllable per tile (glyph tiles reused) the estimate drops to roughly 97/107/78/62, which is still over 80 for 결판 and 순위표. So dense pages need either more borrowed tiles or a Java-drawn layer that follows the same NGPC rules. Sources: WebFetch could not resolve any host and curl was blocked by the proxy, so every web fact below comes from WebSearch result summaries, with URLs. A few specific UI details could not be confirmed and are marked [unverified].

### 제약

- Hard rule: no ROM, save state or ROM-derived image in any repo, artifact or shared file. The mocks use only Galmuri7/11 (OFL) and our own pixel art; game graphics are neutral grey blocks. The matchup grid must keep using our own icons or numbers, never the game's face graphics.
- NGPC rules the design must obey: 160×152 = 20×19 cells of 8×8; one palette (3 colours + transparent) per cell, so colours change only on 8px boundaries; 12-bit colours written as 0x0BGR (practice.c:803); 16 palettes per plane; 64 sprites, most of them the game's; cell H/V flip flags let one tile serve as 2–4 tiles.
- Tile budget is the main risk. The practice menu and the VS band each cap at 80 borrowed tiles. Measured mock pages: 결판 130, 순위표 174, 전적 191, 쉼 78 unique tiles. Estimated with one syllable per tile: ~97/107/78/62. Only the pause window fits the current pool. The others need a measured larger borrow at the post-match moment, or a Java layer that follows NGPC rules.
- Palette budget: the practice menu borrows only 2 unused plane-0 palettes. The full scheme needs about 5 palettes plus one per visible tier, so a 2-palette minimum mode is specified (A = CEF/5BE/012, B = FFF/46E/012). Which game palettes are free or stable after the victory quote is unknown; that is a feasibility question for another track.
- Fonts: the app subsets pixel.ttf, pixel_b.ttf and ink_b.ttf and they lack hanja. 7px hanja inside a 16px seal was illegible in the test, so seals use Hangul (승/패/연/설/위/첫); hanja only as hand-drawn 16px+ art. Galmuri7 (7px Hangul) fits one cell row; Galmuri11 needs two.
- Input: NGPC buttons are A, B, OPTION and the d-pad only, so pages switch with ◀▶ and B means back. Keep B from quitting immediately after a match (cursor moves to 그만하기 first).
- Timing: open/close animations must stay at or under ~0.35 s and be skippable with A. The user prefers short flows («뚜뚜뚜 짧게»), and SF6's fast rematch was a deliberate design goal.
- Research limits: WebFetch failed DNS for every host and curl was refused by the proxy, so all web facts come from WebSearch summaries. Not confirmed from text: the exact SF6 results-screen and LP-gauge layout, Tekken 8's rank-up animation, the hoshitori ○/● sumo convention, and Samurai Shodown 2019's menu art. These are marked [unverified] in the details.
- No adb or emulator was used; the mocks are static PNGs from a Python renderer and have not been checked on a device.

### 기회

- Use the app's existing 먹·금 theme (Theme.java:36-40) converted to 12-bit (CEF washi, 5BE/7DF gold, 46E vermilion, 012 lacquer) as the in-game menu palette. The app shell, the VS band and the in-game menu would then share one identity, with no new branding work.
- One renderer, two back ends: extend RankVs (already outputs NGPC 2bpp tiles plus a map) into a small cell-grid UI renderer. It could stamp the light screens (쉼, 결판 if tiles allow) into VRAM and draw the heavy pages (순위표, 전적) as a 160×152 Java bitmap under the same rules, so they look identical and carry no VRAM risk.
- Cell-aligned glyph tiles (one Hangul syllable per 8×8 tile, digits one per cell like the game HUD) roughly halve tile cost (results 130→~97, leaderboard 174→~107, records 191→~78) and look more like the game's own text.
- Cheap signature effects that need almost no tiles: a 45° slash (1 tile with flips), palette-cycle shimmer on the selected row, a palette flash for the seal slam, row-by-row ink wipes, and a d-pad page wipe that rewrites ≤19 cells per frame.
- Show existing RankCore data as callouts: «설욕전/설욕 성공» (matchmaking already has 12% rival/revenge), «N연승», «오늘 첫 승», «강등 위기!», «배치 n/5», «무쌍 달성», «★ 올라감». All the data already exists in RankCore.settle / Outcome.event.
- Frame the virtual opponents like Samurai Shodown 2019's Dojo ghosts (AI built from player habits, with ghost leaderboards). It gives the nickname CPUs a lore-friendly reason to exist, and their titles (e.g. «무기 파괴자») can serve as Tekken-style title plates on the opponent card.
- Kuroko's red/white flag (the classic SamSho referee), redrawn as our own 8×16 pixel art, could mark the winner on the 결판 window or the VS band. The game already hides Kuroko in the random slot, so it is a strong in-universe motif.
- Retro presentation is a proven premium choice: SF6 sells classic HUDs and offers a retro pixel challenger portrait. That supports keeping everything NGPC-native instead of a modern overlay.
- Leaderboard and record ideas that fit at 160 px: top-3 podium plates in tier colours, my position ±4, filters (전체/같은 티어/내 캐릭터/라이벌), last 10 as ○●, a 5×3 grid by opponent character, a rival line with a chain icon. A on any row opens that player's card with our record against them.

## 2. What makes a fighting-game menu feel "간지" (distilled)
1. **One motif family, used everywhere:** 먹 (lacquer black) + 와시 (washi cream) + 금 (gold) + 주홍 낙관 (vermilion seal). That is exactly the app's 먹·금 theme (Theme.java:36-40: bg 0d0b09, txt efe4c9, accent e0b65d, chg e46a4e).
2. **Big, short headers:** 2-syllable Hangul in Galmuri11 Bold with a 1px shadow, framed by «//  //» diagonal slashes: «결판», «순위표», «전적», «쉼».
3. **One huge result glyph:** a 32×32 hand-pixelled brush «승»/«패» (4×4 tiles), Sekiro-style. If budget is short, a 16×16 seal.
4. **Seal stamps:** chipped vermilion squares, with Hangul inside (도장 feel and legible). Large 16×16: 승 / 패. Small 8×8: 연 (streak), 설 (revenge), 위 (danger), 첫 (first win). Hanja at 7px turned out illegible (tested), so hanja only in hand-drawn 16px+ art.
5. **Diagonal energy:** 45° slash tiles. A 45° line costs 1 tile, because one tile is reused with H/V flips.
6. **A single tapered brush stroke as the separator** (thick head, dry-brush tail), not repeated hazard stripes. I tried the stripes in mock v1 and rejected them.
7. **Tier colour = tier identity** (Tekken), with a 16×16 crest per tier and ★ stars.
8. **Animated LP gauge:** count up, flash at the threshold, then the «승급» seal slams in.
9. **Rival and revenge callouts:** «설욕전», «설욕 성공», «N연승», a chain icon for rivals, «오늘 첫 승».
10. **Glanceability and speed:** three to four options, cursor already on 다음 상대, A works from frame 0 and skips animation. Keep the game visible behind the 결판/쉼 windows (Ghost of Tsushima restraint). Only data-dense pages cover the screen.

## 3. Feasibility on a 160×152 NGPC screen
- **Hardware:** 160×152 out of a 4096-colour (12-bit) space; 16 palettes per plane, 48 in total; 4 colours per tile, colour 0 transparent; 2 scroll planes; 64 sprites of 8×8; tiles shared by planes and sprites. [gametechwiki.com/w/index.php/Neo_Geo_Pocket_Color ; segaretro.org/Neo Geo Pocket Color]
- **Verified in this codebase:**
  - Palette words are **0x0BGR** (practice.c:803; e.g. 0x5EF is yellow).
  - Practice window: 14×13 cells; borrows 2 unused plane-0 palettes (preference 13, 14, 15, 12, 6, 2) and up to **80 unreferenced tiles** (POOL_MAX, practice.c:142-144, 667-680). Cell flags 0x8000/0x4000 = H/V flip.
  - VS band: ≤80 tiles in 0x0D0–0x105 and 0x0B6–0x0CF. Plane-0 palettes 2/3/4/5/9/13/14 stay stable through the intro.
- **One palette per 8×8 cell**, so colour changes only on 8px boundaries. Row highlights are a free palette swap. Per-row tier colours cost one palette per distinct tier.
- **Text:**
  - Galmuri7 Hangul is 7px tall with about 8px advance, so it fits one cell row: put 7px text at y = row×8.
  - Galmuri11 is 11px, so headers span 2 rows (y = row×8 + 2).
  - The app's pixel.ttf, pixel_b.ttf and ink_b.ttf are subset and have no hanja. Galmuri7 (handoff/ss2_practice/stage1/fonts) does.
- **Measured unique tiles** in my mocks (flip-deduped, proportional text): 결판 130 · 순위표 174 · 전적 191 · 쉼 78.
- **Estimate with cell-aligned glyph tiles** (one syllable per tile, reused): about 97 / 107 / 78 / 62.
- **Conclusion:** the pause window fits the practice-style pool. 결판, 순위표 and 전적 need either:
  - (a) a bigger borrow from the 512 tiles while the game is frozen (the number of free tiles at the post-match moment must be measured), or
  - (b) a Java layer drawn at 160×152 under exactly these rules (8×8 cells, ≤3 colours + transparent per cell, 12-bit palette), scaled the same way as the game. RankVs already outputs NGPC 2bpp tiles plus a map, so one renderer could feed both a VRAM back end and a bitmap back end.

## 4. Style guide proposal

**4.1 Palettes (12-bit 0x0BGR; index 0 = transparent; c3 = opaque window fill)**
| Palette | c1 | c2 | c3 |
|---|---|---|---|
| INK | CEF washi text | 789 dim/shadow | 012 lacquer black |
| GOLD (frame, header) | 7DF highlight | 5BE gold | 012 |
| SEAL | FFF glyph | 46E vermilion | 113 deep red edge |
| SEL (selected row) | FFF text | 7DF | 46E vermilion bar |
| GAUGE | FFF flash | 5BE fill | 234 empty track |

- **Tier colours (c1 / c2, c3 = 012):** 수련생 888/444 · 낭인 BBB/666 · 무사 07F/035 · 검객 FFF/888 · 검호 AFF/6AA · 달인 FE7/993 · 검성 22F/118 · 무쌍 FFF with 00E. These match the VS band's tier colours.
- **Minimum mode (2 palettes)** if only two are free:
  - A = {CEF washi, 5BE gold, 012 ink}: text, frame, gauge, brush.
  - B = {FFF, 46E vermilion, 012}: seals, selected row, danger.
  - Tier then shows through the crest shape and text; only my row and the top 3 get a third tier palette.
- When the game's HUD palettes are known to be intact (as in the intro), reuse 2/3/4/5/9/13 the way the VS band does.

**4.2 Typography**
- Headers: Galmuri11 Bold, 2 rows, 1px 789 shadow.
- Body: Galmuri7, 1 row.
- Digits: one per cell, like the game HUD.
- Result splash: hand-pixelled 32×32 brush glyph.
- Galmuri11 for nicknames only in the VS band and the opponent card.

**4.3 Layout grid** (20 cols × 19 rows of 8 px; data-dense pages use the full screen with a 1-cell gold frame)
- **결판** (window cols 1–18, rows 2–17, game visible above and around):
  - r1–2: header tab «//결 판//».
  - r3–4: «승리!»/«패배» 11px plus seal 승/패 at cols 14–15.
  - r5: «2:1 · 상대닉 티어★».
  - r6–7: tier crest (2×2) + LP gauge (10 cells) + «+95»; r7: «무사★3 → ★4  1840».
  - r8: event line in gold (승급 / ★ 올라감 / 강등 위기 / 배치 n/5 / 무쌍 달성).
  - r9: tag seals (연 3연승 · 설 설욕 성공 · 첫 오늘 첫 승).
  - r10: brush stroke.
  - r11–14: ▶ 다음 상대 (default) / 재대결 / 순위 · 전적 / 그만하기.
  - r15: hint «A 결정 · B 그만 · ◀▶ 쪽».
- **순위표:**
  - r1–2: «순위표» + seal + «◀ 전체 ▶» and «시즌 1» on the right.
  - r3–5: three podium plates (1위/2위/3위) in tier colours, crown on 1st.
  - r6: brush.
  - r7–14: 8 rows of my position ±4 («순위 · 닉 · 티어 · LP»); my row in SEL with ▶; rival rows with a chain icon.
  - r16–17: hints «◀▶ 전체·같은 티어·라이벌», «A 이 사람 전적 · B 닫기».
  - Seal glyph: «순» or «위». «방» (榜) reads as "room", so avoid it.
- **전적:**
  - r1–2: «전적» + seal + season/tier.
  - r3: «128전 71승 57패 55%»; r4: «최고 7연승 · 지금 3연승»; r5: «최근 ○○●○○○●●○○».
  - r6: «상대 캐릭터별 (승-패)».
  - r7–15: 5×3 grid of neutral 16×12 face placeholders, each with W-L below (bright if winning, dim if losing). In the real game this would be our own icons or numbers, never ROM faces.
  - r16: «⛓ 라이벌 ChillBee 4-6 · 설욕 대기».
  - r17: hint.
- **쉼** (window cols 3–16, rows 3–15, the same size class as the practice menu):
  - Header «//쉼//».
  - «vs 닉 티어★» / «나와 4-6 · 설욕전».
  - Brush.
  - 이어하기 / 순위 · 전적 / 기권 (−LP shown) / 리그 그만.
  - «B·OPTION 닫기».

**4.4 Transitions** (60 Hz frames; A skips to the end state at any time)
- **Opening, «칼집 열기»:**
  - 0–6f: black bands close from top and bottom (opaque ink rows, 2 rows per frame).
  - 6–10f: one diagonal white-and-gold slash crosses the slit (1–2 tiles reused).
  - 10–16f: the window "ink-spreads" row by row from the centre.
  - 16–22f: the seal slams: c2 flashes to white for 2 frames, plus a 2px shake for 4 frames. Shake the plane-0 scroll only while the game is frozen, or move the seal as sprites.
- **LP gauge:** about 1px per 2 frames (≤40f). Digits tick. At a threshold, gold↔white flashes 3×6f, then the «승급» seal.
- **Page change, «칼 휘두름»:** a column of diagonal tiles sweeps 2 cols per frame (10f); the new page is written behind it.
- **Cursor:** the ▶ blade bobs 1px every 16f, or the gold c1↔c2 of the selected row shimmers every 8f (zero tiles).
- **Close:** reverse ink wipe, 6f.

## 5. Menu structure ideas from the references
- **Entry points:**
  - (1) After the victory quote: the 결판 window opens over the frozen victory pose (replaces today's Java result card).
  - (2) OPTION during a match: 쉼.
  - (3) From 결판 or 쉼: 순위 · 전적 pages, switched with ◀▶.
  - The NGPC pad has only A, B, OPTION and the d-pad, so ◀▶ switches pages and B goes back.
- **Post-match choices:**
  - 다음 상대 (default; SF6's fast flow; the user wanted «뚜뚜뚜 짧게»).
  - 재대결: if I lost, also «재대결 · 스테이지 다시 뽑기» (Tekken 3.01.01).
  - «캐릭터 바꿔 재대결» (SamSho 2019) as a sub-option.
  - 순위 · 전적.
  - 그만하기.
  - B moves the cursor to 그만하기 and a second B confirms, so nobody quits by accident.
  - If rematches are capped as a set, show «재대결 2/3».
  - No auto-advance timer by default; optionally a burning-fuse countdown when a «연속 대전» toggle is on.
- **Callouts:**
  - «설욕전» on the VS band and in 쉼; «설욕 성공» and the revenge bonus in 결판 (Tekken Revenge Bonus).
  - Chain icon for rivals.
  - «오늘 첫 승» (KOF XV daily boost).
  - «강등 위기!» in vermilion.
  - «배치 n/5».

## 시안 — 족자 메뉴: 리그 대전 게임 속 메뉴. Angle 1은 모든 화면을 게임 화면 안에 NGPC 타일 규칙대로 그린다

한 줄 요약: 리그 메뉴 전체를 사무쇼2 화면(160×152) 안에서, NGPC 하드웨어 규칙(8×8 2bpp 타일, 칸마다 4색 팔레트, 12비트 색)만으로 그린다. 그래서 게임에 원래 있던 메뉴처럼 보인다. 156 VS 띠의 방향을 경기 뒤와 쉬는 동안까지 넓히는 셈이다.

■ 디자인 언어: 먹 족자
- 바탕은 옻칠 먹색 족자(012)이고 금박 테두리(5BE·7DF)를 두른다. 글자는 화선지 색(CEF)이다. 앱의 먹·금 테마(Theme.java)를 12비트로 옮긴 색이라 앱 화면, VS 띠, 게임 속 메뉴가 같은 집안처럼 보인다.
- 창 모양은 위·아래 금 축에 손잡이가 달린 족자다. 창이 열릴 때는 족자가 한 줄씩 풀려 내려온다.
- 판정(승/패)은 붉은 낙관(인장) «승»·«패»로 찍는다. 꼬리표는 8×8 작은 낙관(연=연승·설=설욕·첫=오늘 첫 승·위=강등 위기)이다.
- 줄 구분은 붓 한 획(머리는 굵고 꼬리는 마른 붓)이다. 커서는 금빛 단도 ▶이고, 고른 줄에는 진홍 띠를 깐다.
- 글꼴: 큰 글자는 앱의 Galmuri11(pixel.ttf, 12px), 본문은 Galmuri7(8px, 한 칸에 한 줄)이다. 연습 메뉴(practice_glyphs.h)와 같은 계열이다.
- 색: 결판 띠는 VS 띠처럼 게임 HUD 팔레트 값(FFF/666, AFF/07F, 빨강 00E)을 쓰고, 티어 색은 RankVs.TIER_STYLE과 같다.

■ 책 양쪽 끝 배치 (bookend)
- 경기 전: 무대 인트로의 위 검은 띠(20×4칸)에 VS 띠가 뜬다. 가운데 9·10칸은 빨간 VS 상자다.
- 경기 뒤: 걸쇠(0x5825)로 멈춘 승리 화면의 같은 검은 띠, 같은 칸 배치에 «결판 띠»가 뜬다. VS 상자가 있던 자리에 낙관 «승/패»를 쾅 찍고, 진 쪽 글자는 회색으로 꺼진다. 내 LP 숫자는 그 자리에서 차오른다.
- 그다음 그 띠에서 족자가 풀려 내려와 메뉴가 된다. 아래 검은 띠(줄 17~18)에는 고른 줄 설명과 버튼 안내가 들어간다.
- 족자는 진 쪽에 붙여 연다. 이긴 캐릭터의 마지막 자세가 옆에 보이게 하려는 것이다(SF6 결과 화면 느낌).

■ 화면이 뜨는 때 (네 순간 모두 게임 화면 안)

■ 그리는 길: 이 Angle의 핵심 판단
- 처음 생각한 Angle 1은 «VRAM에 직접»(practice.c·vsband.c 방식)이었다. 그런데 조사 A의 실측으로 가장 중요한 순간인 경기 뒤 걸쇠에서는 VRAM이 화면에 나오지 않는다. 코어가 멈춰 있고, 한 프레임만 돌려도 게임이 판 0의 줄 4~16과 스프라이트 표를 다시 쓴다. 6~8프레임 뒤에는 다음 장면으로 넘어간다.
- 타일 수도 맞지 않는다. 목업에서 잰 고유 타일은 결판 187, 순위표 202, 전적 240이다. 경기 중 일시정지 때 안전하게 빌릴 수 있는 타일은 120~130개, 연습 메뉴 풀은 80개다.
- 그래서 «게임 화면 안·NGPC 규칙 그대로»는 지키되, 실제로 그리는 곳은 native.c의 가상 셋째 판(덧판)으로 한다. 덧판은 게임과 같은 160×152 격자 위에 코어의 색 규칙(니블×17 → RGB565 → 8888)으로 합성하므로, 게임 팔레트로 칠한 픽셀과 값이 똑같다.
- 덧판의 규칙도 NGPC와 같다: 타일 512개, 팔레트 16개, 칸마다 팔레트 하나, H/V 뒤집기, 8×8 쿼드, 줄마다 가로 스크롤.
- 이 길에서는 코어 메모리를 건드리지 않는다. 그래서 저장 전 복원, 겹침 검사, 타일 예산이 모두 필요 없다.
- VS 띠는 이미 시험을 통과한 VRAM 방식을 그대로 둔다. 원하면 3단계에서 덧판으로 옮긴다.

## 시안 — 칼집과 두루마리: 리그 인게임 메뉴 (하이브리드안)

리그 대전 안에 따로 두는 인게임 메뉴입니다. 화면은 두 종류이고, 그리는 쪽도 둘로 나눕니다.

(1) 칼집(command window): 게임 화면 위에 바로 뜨는 짧은 명령 창입니다. 경기가 끝난 뒤의 결판, 경기 중 OPTION으로 여는 쉼, 그만할까? 확인 창이 여기에 속합니다. native가 맡습니다. 창틀·낙관·커서·고정 글자는 빌드 때 구워 둔 art bank(lgm_art.h)에서 가져오고, 상태기계·애니메이션·입력도 native에서 처리합니다. 그래서 0x5825 걸쇠로 코어가 멈춘 순간에도 Java를 거치지 않고 프레임 단위로 정확하게 움직입니다. 리눅스 하네스만으로 처음부터 끝까지 시험할 수도 있습니다.

(2) 두루마리(data page): 순위표·전적·시즌·상대 카드처럼 글이 많은 페이지입니다. Java가 맡습니다. RankVs를 일반화한 TileCanvas가 Galmuri7/11로 NGPC 규칙에 맞는 타일·맵·팔레트를 만듭니다. 만드는 일은 백그라운드 스레드에서 하고 결과는 캐시에 둡니다.

두 화면 모두 native.c의 덧판(가상 overlay plane) 하나로 합성합니다. 규칙은 160×152 격자, 8×8 칸마다 팔레트 하나(3색 + 투명), 12비트 0x0BGR 색을 ×17로 펼치는 게임과 같은 색 규칙입니다. 조사 A에서 걸쇠 순간에는 VRAM에 그려도 화면 가운데에 안 보인다는 것이 확인돼서, '네이티브 창 = VRAM 타일'이라는 하이브리드 원안을 이렇게 바꿨습니다. 창의 주인은 native, 페이지의 주인은 Java로 나누고, 그리는 곳은 하나로 모읍니다. 예전처럼 VRAM에 찍는 길(practice.c 창 엔진)은 쉼 창의 비상용으로만 남깁니다.

디자인 언어: 칼집은 옻칠 먹(012), 금(5BE/7DF), 주홍 낙관(46E)입니다. 두루마리는 한지(CEF) 위에 먹 글씨와 주홍 낙관, 위아래에 옻칠·금 축을 둡니다. 둘 다 앱 Theme(먹·금)을 12비트로 옮긴 것이고 VS 띠의 티어 색과 맞춥니다. 결판의 머리 줄은 게임이 걸쇠 화면에 이미 남겨 둔 위 검은 띠(0–31px)에 씁니다. 경기 전 VS 띠가 섰던 바로 그 자리라서, VS 띠로 시작해 결판 띠로 끝나는 짝이 됩니다. 아래 검은 띠(136–151px)에는 꼬리표와 안내를 둡니다. 가운데에서는 멈춘 승리 포즈가 그대로 보이고, 오른쪽에서 칼집 패널(72px)이 미끄러져 들어옵니다.

왜 이 방향인가
- 유저가 좋아한 것은 «게임 인터페이스 친화». 그래서 모든 화면을 NGPC 규칙대로 그린다: 8×8 칸, 칸마다 4색 팔레트 하나, 12비트 색, 160×152. 색은 앱의 먹·금 테마와 게임 HUD 티어색을 쓴다. Java 카드처럼 게임 위에 떠 있는 느낌이 아니라 게임 화면 안에 있는 느낌이 나야 한다.
- «간지»는 화면을 많이 넣어서가 아니라 순간 하나로 낸다. SF6처럼 빠른 다음 판, Sekiro처럼 큰 글자 하나(승·패 도장), 사무라이 스피리츠의 섬광 베기, Tekken처럼 색만 봐도 아는 티어와 다음 단계까지의 막대. 연출 길이는 무슨 일이 있었는지에 따라 달라진다:
  - 평범한 승리: 약 1.0초
  - ★ 상승과 호명 띠: 약 1.4초
  - 승급: 약 1.8초
  - 어느 때든 A를 누르면 곧바로 끝 장면으로 간다.
  유저가 원한 «뚜뚜뚜 짧게»를 지킨다.
- «진 쪽에 막을 내린다»는 이 기획의 연출 규칙이다. 내가 이기면 막이 오른쪽(CPU 쪽)에 내려와 내 승리 포즈가 그대로 보인다. 지면 왼쪽에 내려와 상대 승리 포즈가 보인다. 상대 승리 포즈는 «설욕 대기» 띠와 이어진다.
- 가짜 데이터는 정직하게 보인다. 순위표와 명패에는 늘 «CPU» 표를 단다. 4만 명은 «도장 40,000명», 곧 사무라이 스피리츠 2019 도장 고스트처럼 AI 검객이라는 설정으로 부른다.
